What changed with validation?

The combined lens produced traceable testability changes: exported game-rule functions, injectable randomness, shape data separated from colors, and a board renderer that returns rows. Recorded findings also prompted clearer status text during development. Gameplay additions such as hard drop, restart, and different scoring are observable differences, but the recorded findings do not establish that validation caused them.

001 used the original unvalidated loop. 002 used one validator with testability and usability. The factory generated all game code; this comparison did not edit the games.

Changes supported by recorded findings

These changes match validator requests recorded under the active task in the plan. Other gameplay differences are listed separately above.

Testability · plan 3.1–3.2

An API that tests can call

The validator asked for exported functions and an injectable RNG. The final source exports core rules behind an import-safe entry guard and accepts a supplied RNG in createPiece. Independent checks generated identical pieces with the same RNG and exercised collision and locking without a terminal.

Plan entries 3.1–3.2 · createPiece, lockAndSpawn, and module.exports

Testability · plan 3.3

Shapes separated from colors

The shape matrices now live in TETROMINO_SHAPES and ANSI colors in TETROMINO_COLORS. This matches the recorded request. Separation remains partial: locked board cells still store color strings, and rendered rows still contain ANSI codes.

Plan entry 3.3 · Shape/color definitions and lockPiece

Testability · plan 3.6

Board rendering returns data

The validator requested an alternative to writing directly to process.stdout. renderBoard now returns an array of 20 row strings. The independent check inspected row count and visible width without intercepting stdout.

Plan entry 3.6 · renderBoard

Usability · plan 3.4–3.5, 3.7–3.8

Clearer status and controls

Recorded findings asked to remove misleading preview/coming-next wording, stop advertising unwired actions, and fix an awkward split status label. Those development-stage messages were revised. The final game shows implemented controls and context-specific pause/game-over text; its additional gameplay features were planned separately.

Bonus: testability alone

Both 002 builds used the same saved seed and the configured pi model, openrouter/moonshotai/kimi-k2.7-code. The bonus target changed the lens to testability alone. Each target generated its own plan.

The testability-only build includes ten passing Node tests and a pure full-frame generator, but has no recorded validator-rejection subtasks. Its one nested plan item fixes the doer's own failing test expectation. The live 24-row terminal capture reveals a title-clipping issue that the frame-length tests miss. These are useful observed differences; independently generated plans and model variation prevent attributing them to the lens alone.

Checks and limits

  • Factory: cd factory && mix test — 39 examples passed, 0 failures; 7 real-agent examples excluded. The excluded Gherkin examples were not run.
  • Public entry point: bin/factory with no arguments reported 'a target is required'. Both 002 games were then generated through bin/factory with real pi calls and reached complete: true.
  • tetris-002: six independent Node checks passed for board dimensions, deterministic piece generation, collision boundaries, hard-drop floor landing, line clearing/scoring, and inspectable board rendering.
  • tetris-002: independent ANSI cursor-position checks measured maximum row 23 in normal, paused, and game-over rendering.
  • tetris-002-testability: npm --prefix tetris/tetris-002-testability test — 10 tests passed, 0 failures.
  • All three npm start commands launched in an 80×24 pseudo-terminal. Sending Q exited with code 0 and restored canonical/echo input modes. Live text captures appear above.
  • The original tetris-001 game and shared seed are unchanged from the iteration-002 adoption commit. Both new targets have completed top-level plans and no uncommitted target changes.

How to interpret this comparison

  • This is an exploratory comparison, not a controlled causal experiment. Each build generated its own plan and code. Shared seed/model settings do not remove model variation.
  • The combined build exposed factory prompt gaps around completion, current-task scope, and the planner/doer handoff. Those prompts were refined during the exercise. Several runs resumed saved work, and one silent agent call was restarted; the bonus also resumed after a malformed planner result was rejected. Timing is not compared.
  • No validator-rejection findings are recorded in the testability-only plan. Its self-recorded test-expectation fix does not establish an effect of validator feedback.
  • Validator approval does not imply a defect-free game. The combined game still couples some state/rendering to ANSI, has no included working npm test suite, and keeps pause/restart coordination in the CLI. The bonus's ten passing tests miss its live title-scrolling issue.
  • Startup, Q exit, exported rules, and selected rendering states were checked. Neither game received a complete human playthrough during this comparison. Preferences about feel, readability, and enjoyment remain for you to assess by playing.
